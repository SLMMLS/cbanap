# ClipSync for Android

Компаньон к ClipSync на ПК. Реализует протокол из `../PROTOCOL.md` —
сопряжение по QR и синк буфера по локальной сети.

Что изменилось в последней ревизии и почему — в [`../CHANGES.md`](../CHANGES.md).

## Состояние проверки — честно

**Полную сборку APK (Gradle + Android SDK) в среде разработки выполнить не
удалось.** Там нет Android SDK, а DNS для `dl.google.com`,
`maven.google.com`, `services.gradle.org` и `repo.maven.apache.org` не
резолвится (сеть ограничена белым списком), то есть нельзя ни поставить SDK,
ни скачать Gradle, ни скачать AndroidX/Compose. Вместо этого сделано то, что
технически возможно:

| Что | Чем проверено | Результат |
|---|---|---|
| Весь не-UI код: `crypto/`, `network/`, `data/`, `service/`, `boot/`, `share/` | настоящий `kotlinc 2.0.21` (версия проекта) против `android.jar` API 34 + BouncyCastle + NanoHTTPD 2.3.1; OkHttp, Room, AndroidX-core — через стабы с теми же сигнатурами | компилируется, 0 ошибок |
| `MainActivity` (навигация, sealed-состояние) | `kotlinc` против стабов Compose/Navigation | типизируется |
| Compose-экраны (`HomeScreen`, `SettingsScreen`, `PairingScreen`) | только парсер `kotlinc` (синтаксис) + ручная сверка каждого импорта и вызова | синтаксис чист; **семантику Compose компилятор не проверял** |
| `SyncServer`, `CryptoUtils`, `Identity.sharedSecret`, `PinningTrustManager`, `PairingQrPayload`, `NetworkErrors` | **запущены на JVM** (подменены только `android.util.Base64/Log`) против настоящего серверного кода ПК: сопряжение, пуш в обе стороны, pinning (верный/испорченный хэш), атаки на приёмник | 31 сквозной сценарий вместе с сервером ПК и 14 сценариев атак на приёмник — все проходят |
| Серверная часть ПК (`server.rs`, `sync.rs`, `discovery.rs`, `pairing.rs`, `storage.rs`, …) | собрана `rustc 1.91` с точными версиями крейтов проекта; `tauri` и системный `keyring` заменены заглушками | собирается; те же 31 сквозных сценария проходят |

**Что осталось непроверенным и проверяется только на вашей стороне:**

- сама Gradle-сборка (версии AGP/Kotlin/KSP/Compose-BOM — см. п. «Если сборка не
  пройдёт»);
- семантика Compose-экранов, CameraX + ML Kit в `PairingScreen`;
- OkHttp 4.12 (в тестах транспорт заменён на JDK `HttpsURLConnection`, то есть
  реальные таймауты, ALPN и пул соединений OkHttp не гонялись);
- реальное поведение foreground-сервиса и Keystore на устройстве (по
  документации Android; в тестах не воспроизводимо без устройства).

### Если сборка не пройдёт с первого раза

От наиболее вероятного к наименее:

1. **Версии Gradle/AGP/Kotlin/KSP в `build.gradle.kts`** — самый частый источник
   проблем в любом Android-проекте. Android Studio обычно сама предлагает апгрейд.
   Для пары Kotlin/KSP есть таблица соответствий на странице релизов KSP.
2. **`PairingScreen.kt`** — стык CameraX + ML Kit + Compose.
3. **Compose-экраны** — это единственный код, который ни разу не проходил
   семантическую проверку компилятором.
4. Остальное — стандартные паттерны (Room, OkHttp, NanoHTTPD, Android Keystore).
   `Identity.sharedSecret` и `PinnedHttp` теперь исполнялись реально: X25519/HKDF/
   AES-GCM побайтно совпадают с Rust-кодом ПК, а pinning отвергает сертификат с
   одним изменённым байтом.

## Почему «не коннектилось» — что найдено при разборе

Протокол сам по себе исправен: TLS, pinning, X25519+HKDF+AES-GCM и транспорт в
обе стороны совпадают между Rust (ПК) и Kotlin (телефон). Причины были в
окружении Android, сети и потоке UI. По убыванию вероятности:

1. **Android 14+ и foreground-сервис `connectedDevice`.** Начиная с `targetSdk 34`
   система при `startForeground()` проверяет предусловия типа сервиса. Для
   `connectedDevice` в манифесте обязано быть хотя бы одно из:
   `CHANGE_NETWORK_STATE`, `CHANGE_WIFI_STATE`, `CHANGE_WIFI_MULTICAST_STATE`,
   `NFC`, `TRANSMIT_IR` (или Bluetooth/UWB-разрешение во время выполнения). Их не
   было — `ReceiverService.onCreate()` падал с `SecurityException`, а так как
   сервис стартует сразу после успешного сопряжения (и при каждом запуске, пока
   ПК сопряжён), приложение **вылетало сразу после сопряжения и при каждом
   открытии**. Исправлено: добавлено `CHANGE_NETWORK_STATE`; кроме того, любая
   отказ `startForeground()` теперь ловится, логируется и показывается, а не
   роняет приложение.
2. **Брандмауэр Windows / профиль сети «Общедоступная».** Кодом не лечится. Вместо
   молчаливого таймаута телефон теперь пишет, что это, скорее всего, брандмауэр,
   а ПК показывает статус сервера и свои адреса. Команда для правила — в
   основном `README.md`.
3. **Неверный IP в QR.** ПК брал адрес «по маршруту в интернет»; при VPN, Hyper-V,
   WSL или VirtualBox это адрес не той сети. QR теперь несёт все приватные
   адреса ПК (`alt`), телефон перебирает их и запоминает сработавший.
4. **Автоповтор сканирования сжигал одноразовый токен и прятал первую ошибку.**
   После неудачи QR всё ещё перед камерой, анализатор сразу слал второй запрос,
   ПК отвечал `403`, и на экране оставалось только «код 403». Теперь сканирование
   останавливается, показывается настоящая причина и кнопка «Сканировать снова».
5. **Один зависший клиент блокировал сервер ПК целиком.** У `tiny_http` нет
   таймаутов чтения, а старый цикл обрабатывал запросы по одному; клиент,
   замолчавший посреди загрузки картинки, делал ПК глухим для всех. Доказано
   тестом (старый код: следующий запрос не отвечен за 5 с; новый: 0,04 с).
6. **Повторное сопряжение с тем же ПК после его переустановки** оставляло в Room
   две строки, а `SELECT … LIMIT 1` без `ORDER BY` мог вернуть устаревшую.
   Теперь перед сохранением таблица очищается (в одной транзакции).
7. **Стартовый экран.** `null` в качестве «БД ещё не ответила» неотличим от «ПК не
   сопряжён», поэтому при каждом запуске показывался QR-сканер, хотя пара есть.
8. **Тихие отказы.** Кнопка «Отправить» глотала любую ошибку; теперь результат
   виден в снэкбаре.

## Диагностика, если всё равно не подключается

1. **На телефоне: Настройки → «Проверить связь с ПК».** Покажет отдельно:
   телефон → ПК (TCP, TLS, сертификат), ПК → телефон (слушает ли приёмник и
   почему нет), адреса телефона (и предупредит о VPN).
2. **Журнал телефона** (USB-отладка включена):
   ```
   adb logcat -s ClipSync:V AndroidRuntime:E
   ```
   Все сетевые сбои и отказы системы пишутся под тегом `ClipSync` с полным
   стеком.
3. **Жив ли сервис:** `adb shell dumpsys activity services com.clipsync.app`.
4. **ПК → телефон с компьютера** (PowerShell): `Test-NetConnection <IP телефона> -Port 47990`.
   `TcpTestSucceeded : True` — приёмник телефона доступен.
5. **Телефон → ПК:** на ПК в Настройки → Устройства статус должен говорить «Сервер
   синхронизации работает», а адреса ПК должны включать адрес вашей Wi-Fi сети.

## Чек-лист требований безопасности Android

| Требование | Состояние |
|---|---|
| Тип foreground-сервиса объявлен и его предусловия выполнены (Android 14+) | да, `connectedDevice` + `CHANGE_NETWORK_STATE`; отказ системы не роняет приложение |
| `android:allowBackup` | **выключено** (раньше `true`): ключи обёрнуты Keystore-ключом, который не переносится между устройствами, и восстановленная копия приводила к краху при расшифровке |
| Cleartext-трафик | **выключен** в `network_security_config.xml` (раньше `true` глобально). Исходящий трафик — только pinned HTTPS; приём `/push` на слушающем сокете политикой не регулируется |
| Pinning самоподписанного сертификата ПК | да, SHA-256 DER из QR; несовпадение — отдельное исключение `PinMismatchException`, проверено на испорченном хэше |
| Экспортируемые компоненты | экспортированы только `MainActivity` (launcher) и `ShareReceiverActivity` (обязательно для «Поделиться»); сервис и `BootReceiver` — нет |
| Недоверенный ввод | QR валидируется (версия, токен, 32-байтный хэш, только IPv4-литералы); `ShareReceiverActivity` принимает только `content://` (не `file://`), читает с лимитом, декодирует в IO-потоке с субсэмплингом |
| Приёмник, открытый на LAN | заголовки → лимит размера → известный отправитель → и только потом чтение тела; ранние отказы закрывают соединение; тело ≤ 24 МБ |
| Секреты на диске | приватный X25519 и ключ БД — под AES-GCM-ключом из Android Keystore; запись в prefs синхронная (`commit`), чтобы сбой не оставил Keystore-ключ без обёрнутого секрета |
| `PendingIntent` | `FLAG_IMMUTABLE` |
| Уведомления | без содержимого буфера |
| Анти-перебор токена сопряжения (на ПК) | 5 неверных токенов закрывают окно |
| Повторное воспроизведение (replay) `/push` | **не закрыто**: в формате есть `created_at`, но он не проверяется. AES-GCM защищает от подделки, не от повторной отправки перехваченного пакета |
| Метаданные в открытом HTTP (ПК → телефон) | видны наблюдателю в сети (кто, когда, сколько); содержимое зашифровано. Закрывается TLS на стороне телефона — отдельная задача |

## Дорожная карта `targetSdk` (не сделано сознательно)

Сейчас `compileSdk/targetSdk = 34`: приложение ставится и работает на Android 14,
15, 16 и 17 вручную (sideload). Менять уровень без реальной сборки я не стал —
это цепочка зависимостей (AGP, Gradle, Kotlin, Compose-BOM), которую нужно
проверять компиляцией. Что нужно знать:

- **Google Play** (только если будете публиковать): новые приложения и
  обновления обязаны таргетить **API 36** (требование действует с 31 августа
  2026). Для установки APK вручную это не требуется.
- **Android 17 (API 37): разрешение `ACCESS_LOCAL_NETWORK`.** Для приложений с
  `targetSdk 37` доступ к локальной сети (а ClipSync — это именно LAN-приложение, и
  исходящее, и входящее направление) станет runtime-разрешением. При апгрейде до 37
  его нужно объявить и запрашивать до сопряжения; до тех пор приложение с
  `targetSdk 34` этим не затрагивается.
- Попутно при апгрейде: принудительный edge-to-edge (API 35+), выравнивание
  нативных библиотек под страницы 16 КБ (ML Kit, CameraX), предиктивный жест
  «назад».

## Сборка

**Android Studio:** откройте папку `android/` (не весь `clipsync`), дождитесь
Gradle Sync, запускайте на реальном телефоне (сопряжение по LAN через
эмулятор устроено сложнее из-за NAT).

**Без Android Studio — GitHub Actions:** запушьте репозиторий на GitHub →
Actions → «Android APK» → артефакт `clipsync-debug-apk`
(`.github/workflows/android.yml`; Gradle 8.9 ставится самим workflow'ом, SDK уже
есть на раннере). Debug-APK подписан отладочным ключом, для установки на свой
телефон достаточно.

**Из консоли:** `gradle wrapper --gradle-version 8.9` один раз создаёт
`gradlew`, затем `./gradlew :app:assembleDebug`.

Телефон и ПК должны быть в одной Wi-Fi сети (не гостевой).

## Что реализовано

- Сканирование QR из настроек ПК → HTTPS (pinned по хэшу сертификата из QR)
  POST `/pair` по всем адресам из QR → сохранение пары в Room.
- Приём `/push` с ПК через foreground-сервис (тип `connectedDevice`) — работает,
  даже если приложение свёрнуто; уведомление о новом элементе. Приём остаётся на
  обычном HTTP (`PROTOCOL.md` §2a — почему асимметрично).
- Отправка на ПК двумя путями: кнопка в приложении и системное «Поделиться» из
  любого приложения (`ShareReceiverActivity`) — без чтения буфера в фоне, которого
  Android всё равно не даст с версии 10.
- Локальная история (Room) зашифрована отдельным AES-256-ключом, обёрнутым ключом
  Android Keystore (сам Keystore X25519 на всех устройствах одинаково надёжно не
  генерирует, поэтому raw-ключ создаётся в софте и хранится завёрнутым).
- Перезапуск приёмного сервиса после перезагрузки телефона (`BootReceiver`).
- Диагностика: «Проверить связь с ПК», понятные тексты ошибок, журнал `ClipSync`.

## Чего нет

Ретраев/очереди для офлайн-ПК, perfect forward secrecy, защиты от replay,
настраиваемого порта, автоматического поиска ПК по mDNS при смене его адреса
(если IP ПК изменился, нужно сопрячься заново), TLS для направления ПК → телефон.
UI — полноэкранное Material 3, а не «стекло» ПК-версии.

## Разрешения — зачем каждое

| Разрешение | Зачем |
|---|---|
| `CAMERA` | сканировать QR при сопряжении |
| `INTERNET`, `ACCESS_NETWORK_STATE`, `ACCESS_WIFI_STATE` | связь по локальной сети; список адресов телефона в диагностике |
| `CHANGE_NETWORK_STATE` | **обязательное предусловие** типа `connectedDevice` на Android 14+ (обычное разрешение, выдаётся при установке); без него сервис приёма не стартует |
| `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_CONNECTED_DEVICE` | держать приёмник живым, пока телефон включён |
| `POST_NOTIFICATIONS` | уведомление о новом элементе с ПК (Android 13+) |
| `RECEIVE_BOOT_COMPLETED` | поднять приёмник после перезагрузки без открытия приложения |
